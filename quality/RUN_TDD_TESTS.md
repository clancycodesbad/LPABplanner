# TDD Verification Protocol

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-09-26 · Project: LPABplanner

## Framework

This project has no existing test infrastructure. Per PROGRESS.md's documented choice, `quality/test_functional.mjs` and `quality/test_regression.mjs` use Node's built-in `node:test` module (available without any install on Node ≥18; verified present at Node v22.14.0 in this environment) with the native `assert/strict` module. No new dependency is added to the project itself — the test files live entirely under `quality/` and are never referenced by `index.html` or any project source file.

## Red-Green Execution Steps

For each confirmed bug in `quality/BUGS.md` with a fix patch:

1. **Red:** Ensure the fix patch is NOT applied (revert if necessary: `git apply -R quality/patches/BUG-NNN-fix.patch`). Run the specific regression test: `node --test --test-name-pattern="BUG-NNN" quality/test_regression.mjs`. It must fail (or, for source-inspection-style regression tests, assert the documented-gap condition holds). Capture output to `quality/results/BUG-NNN.red.log` with `RED` as the first line.
2. **Green:** Apply the fix patch: `git apply quality/patches/BUG-NNN-fix.patch`. Re-run the same test command. It must pass. Capture output to `quality/results/BUG-NNN.green.log` with `GREEN` as the first line. Then revert the fix patch again (`git apply -R ...`) to leave the actual source tree unmodified, per the Phase 5 source-edit guardrail — patches are proposals, not applied changes, in this run.

For confirmed bugs with **no** fix patch (e.g. those requiring a human product decision per QUALITY.md's Human Gate — REQ-006's scoping question, REQ-021's ordering question), only the Red phase runs; `green_phase` is recorded as `"skipped"` and `verdict` as `"confirmed open"`.

## Spec-Grounded Test Requirements

Every regression test's assertion messages and comments cite: the REQ-NNN it violates, the BUG-NNN tracking it, and (where a Tier 4 README passage applies) a short quote of the relevant README language. Since this project has 0 Tier 1/2 formal-spec requirements, "spec basis" for each bug is either the README (Tier 4) or the code's own internal contract (Tier 3 — code-is-the-spec, e.g. "REQ-005 and REQ-006 live in the same function and one is unconditionally scoped while the other isn't — the inconsistency is between two parts of the code itself, not against an external spec").

## Language-Aware Test Execution Commands

- Full regression suite: `node --test quality/test_regression.mjs`
- Single bug: `node --test --test-name-pattern="BUG-NNN" quality/test_regression.mjs`
- Full functional suite (baseline sanity check, run before and after any TDD cycle): `node --test quality/test_functional.mjs`

## Traceability Table

Populated in Phase 5 as `quality/TDD_TRACEABILITY.md`, mapping Bug ID → Requirement ID → Spec basis (README passage or code-internal contract) → Behavioral contract → Test file:function → Red result → Green result.

## Structured Output

`quality/results/tdd-results.json` follows the exact schema in SKILL.md (fields: `schema_version`, `skill_version`, `date`, `project`, `bugs[]`, `summary`). No JUnit XML reporter is available for `node:test` without an added dependency (`node --test`'s built-in TAP/spec reporters do not produce JUnit XML natively); `junit_available: false` is recorded honestly in each bug's sidecar entry rather than fabricating XML output.

## Bug Writeup Generation

Every confirmed bug gets a `quality/writeups/BUG-NNN.md` per the 8-section template (Summary, Spec reference, The code, Observable consequence, [Depth judgment if warranted], The fix — always with an inline diff, The test, [Related issues if any]).
