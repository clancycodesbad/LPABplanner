# Quality Constitution

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-09-26 · Project: LPABplanner

## 1. Purpose

For LPABplanner, "fitness for use" means: a student can build a multi-year enrollment plan, trust that everything they placed is still there when they come back to it, and trust that the tool will actually warn them about a real scheduling conflict — not just the conflicts that happen to fall in whichever semester the tool currently treats as "current." Quality here is not "the code runs without throwing." It is "the plan a student sees on screen matches the plan they actually built, and every conflict the tool is capable of detecting gets detected regardless of which semester it's in."

Deming's "quality is built in, not inspected" applies directly to this project's maintenance model: the twice-yearly data update (`subjects.js`/`archive.js`) is performed by a volunteer, possibly non-programmer, maintainer working from a published PDF under time pressure. Quality has to be built into the code paths that consume that data (defensive parsing, clear failure signals) rather than relying on the maintainer to inspect their own work for transcription errors. Juran's "fitness for use" means specifically: does the clash detector protect the student from the real-world consequence (a missed or double-booked exam) it exists to prevent, in every situation a real plan can reach — not just the one "current term" situation that happens to be tested in practice.

## 2. Coverage Targets

| Subsystem | Target | Why |
|---|---|---|
| `engine.js` (validation, clash detection, progress) | 100% branch coverage of pure logic | This is the entire safety net of the app — a missed branch here (e.g. the current-term-only exam-clash guard) is a real scheduling conflict a student never gets warned about. |
| `js/utils/datetime.js` | 100% of documented format + at least 3 malformed-input cases | The single point of failure for a hand-maintained, twice-yearly data update; a parsing gap here silently degrades exam-clash protection and exam-date display (REQ-007). |
| `js/services/stats-service.js` | Core derivation functions (`effectiveFail`, `normalisedBands`, `sortedTerms`) fully covered including v1/v2 scheme boundary and DNS=0 edge case | This module has zero DOM dependency and is fully unit-testable; a wrong fail-rate calculation misleads students about which subjects are historically hardest. |
| `js/state/planner-state.js` / `storage.js` | Every persistence path (success + storage-throws) covered | Silent data loss (a subject a student thinks they placed simply isn't there next session) is the single worst possible failure for a planning tool. |
| UI modules (`ui-*.js`) | Requirement/contract documentation + manual/integration verification, NOT full Node-executable unit coverage | DOM-dependent; the project's zero-build-step constraint means no headless-DOM tooling is bundled. Covered instead via `RUN_INTEGRATION_TESTS.md`. |

## 3. Coverage Theater Prevention

Examples of tests that would *look* useful for this specific codebase but would not catch real bugs — avoided in `test_functional.mjs`:

- Asserting `Engine.calculateProgress({})` "doesn't throw" without asserting the actual returned counts — this is exactly the kind of test that would still pass if `calculateProgress` silently swapped `compulsory`/`elective` counts.
- Asserting `parseExamDate('8 Sep 2026, 9.00 am') instanceof Date` without asserting the actual date/time values — this would pass even if the day/month/year/hour were all parsed backwards.
- Mocking `localStorage` to always succeed and never testing the throw-path — this is the *one* path (REQ-014) whose entire reason for existing is the failure case; a mock that never fails proves nothing about it.
- Asserting `getClashingSubjects` "returns an object" without asserting which specific subject IDs are keys and what warning strings they contain — the current-term-only exam-clash gap (REQ-006) would be invisible to a test this shallow.

## 4. Fitness-to-Purpose Scenarios

**Scenario 1 — A student drags a subject from a full semester to another full semester and loses it entirely.**
What happened: Because `handleDrop` (`ui-board.js:215-228`) and `onPointerUp` (`ui-touch-dnd.js:123-144`) both call `PlannerState.removeSubject` on the source semester *before* calling `handleAddSubject` on the target, and neither checks whether the subsequent add will succeed, a student who drags a subject between two already-full (4-subject) semesters has that subject silently removed from its original slot and rejected from the new one — it reverts to the pool with only an easily-missed error banner as any indication something went wrong. At scale, a student actively rebalancing a dense, near-complete multi-year plan (exactly the kind of user who has been using this tool the longest and has the most invested) is the most likely to trigger this, and the failure mode looks like "my subject just disappeared," which is maximally confusing because nothing in the UI explains where it went.
How to verify: `test_functional.mjs` — `addSubject failure does not restore removed subject (documents CB-1 gap)`.

**Scenario 2 — A student plans two clashing exams into next year and gets no warning.**
What happened: `Engine.getClashingSubjects`'s exam-clash branch (`engine.js:81`) only executes `if (semesterId === currentTerm)`. A student using the onboarding wizard's suggested-pathway feature (which explicitly plans 8 semesters — years — ahead) or manually planning ahead has zero exam-clash protection for every semester except the one currently active. Two subjects with an identical exam date-time placed in `winter2028`, say, produce no warning at all, even though the exact same two subjects in the current term would be flagged immediately.
How to verify: `test_functional.mjs` — `exam clash — NOT flagged in future term (documents gap)`.

**Scenario 3 — A mistyped exam date in next semester's data update looks like a real date and evades clash detection simultaneously.**
What happened: Because `getExamText` (`ui-board.js:19-43`) displays `subject.exam` directly without validating it through `parseExamDate`, while `examTimesClash` (via `engine.js`) does route the same string through `parseExamDate` and silently treats an unparseable result as "no exam" — a single transcription slip in the twice-yearly hand-maintained `subjects.js` update (e.g. `'8 Sept 2026, 9.00 am'` instead of `'8 Sep 2026, 9.00 am'`) is displayed to every student as if it were a perfectly valid exam date, while being completely invisible to the clash detector. The maintainer gets a console warning nobody is watching for; students get a wrong-looking-right date and no clash protection for that subject.
How to verify: `test_functional.mjs` — `parseExamDate — unrecognized month returns null` (proves the silent-failure half) cross-referenced against the documented display-layer gap in REQUIREMENTS.md REQ-007(d)/REQ-020(d).

**Scenario 4 — A single bad key in the hand-maintained stats registry crashes the entire pool and board render.**
What happened: `data/stats/index.js` is maintained by uncommenting export lines (per its own header comment). `sortedTerms()` in `stats-service.js:27-35` calls `.match(/\d{4}/)[0]` on every key with no null-guard. Since every subject pool item and board slot calls into the stats-derived difficulty badge/grade bar on every render, a single malformed key added during a future stats update throws an uncaught exception that breaks rendering for the *entire* pool and board — not just the one subject with bad data — turning a data typo into full app breakage for every user.
How to verify: `test_functional.mjs` — `sortedTerms — malformed term key does not silently corrupt (documents crash risk)` (a defensive/documentary test given the current dataset is well-formed; see Notes).

## 5. AI Session Quality Discipline

- Never touch `html file version/LPABPlannerApp.html` — it is an explicitly stale, out-of-scope snapshot (README's own instruction to LLMs/agents).
- Never add logic to `planner.js` — it is a re-export shim only (README's own instruction).
- Respect the "one module, one concern" boundary the README states explicitly — if a change touches more than one module's stated responsibility, that's a signal to reconsider the change's scope, not to proceed.
- Any change to the exam-date string format in `subjects.js`/`archive.js` must be paired with a corresponding change to `js/utils/datetime.js`'s parser — the README states this explicitly and REQ-007 encodes it as a testable requirement.
- Any fix to the drag-and-drop remove-then-add pattern (Scenario 1 / CB-1) must be applied to **both** `ui-board.js`'s `handleDrop` and `ui-touch-dnd.js`'s `onPointerUp` — they are parallel, independently-maintained implementations of the same operation (see EXPLORATION.md's Cross-Implementation Consistency deep dive).

## 6. The Human Gate

- Whether the exam-clash current-term-only scoping (REQ-006/Scenario 2) is intentional (e.g., "future timetables aren't reliable enough to warn on") or an oversight requires a maintainer/domain-owner decision — Phase 3/4 will investigate but the final call on whether to widen the check's scope is a human product decision, not a code-review verdict.
- Whether the markdown export's alphabetical (vs. chronological) semester ordering (REQ-021/CB-6) is worth fixing is a human judgment call about how much it actually confuses users in practice — it never produces a *wrong* export, only a differently-ordered one.
- Any fix that touches the twice-yearly maintenance procedure documented in the README must be validated against that documented procedure by a human before being considered complete, since an AI session cannot verify the fix against the *next* real LPAB timetable PDF (which doesn't exist yet).
