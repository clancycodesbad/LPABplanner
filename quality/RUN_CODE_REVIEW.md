# Code Review Protocol

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-09-26 · Project: LPABplanner

Three independent passes, run with no shared context beyond `quality/REQUIREMENTS.md`. Each pass is a fresh review — do not let Pass 2's requirement-driven focus bleed into Pass 1's structural read, and vice versa.

## Pass 1 — Structural Review

Read `engine.js`, `js/utils/datetime.js`, `js/state/planner-state.js`, `js/state/storage.js`, `js/services/stats-service.js`, `js/data/suggested-pathway.js`, `js/ui/ui-board.js`, `js/ui/ui-pool.js`, `js/ui/ui-touch-dnd.js`, `js/ui/ui-onboarding.js`, `js/ui/ui-toolbar.js`, `js/ui/ui-progress.js`, `js/ui/ui-stats.js`, `js/ui/ui-main.js` in full — read function bodies, not just signatures.

Guardrails:
- Line numbers are mandatory for every finding.
- If unsure whether something is a bug: flag as QUESTION, not BUG.
- Grep before claiming a function/case is missing.
- Do not flag style issues — only incorrect behavior.

**Mandatory scrutiny areas:**

1. **Input validation and boundary handling.** This app has one real external-data trust boundary: the hand-maintained data files (`subjects.js`, `archive.js`, `data/stats/*.js`) and the `localStorage`-persisted plan (which the user's own browser controls and could theoretically contain corrupted/tampered JSON after a failed write or manual devtools edit). Check: does `loadPlan()`'s JSON.parse failure path (`storage.js:20-28`) fully cover a *partially* valid but structurally wrong object (e.g. a parsed value that's an array instead of an object)? Does anything downstream assume `_plan[semesterId]` is always an array without checking?
2. **Resource lifecycle.** Not classically applicable (no file handles, sockets, or locks) — but check event-listener lifecycle in `ui-touch-dnd.js`'s `attachTouchHandlers` (remove-then-add pattern, `ui-touch-dnd.js:175-192`) for any leak across repeated re-renders, and check whether `window.removeSubject`/`window.markCompleted` (`ui-board.js:230-242`) being globally reassigned on every module load could ever double-bind or leak in a way that matters for this single-page app.
3. **Concurrency and state management.** No true concurrency (single-threaded browser JS, no workers/async races in the reviewed modules) — but check for logical race conditions between rapid successive user actions: can a double-drop (e.g. rapid double-tap on touch) call `handleAddSubject` twice before the first render completes, given `renderPlannerBoard`/`renderSubjectPool` are synchronous but DOM event handlers could theoretically fire re-entrantly? Check `PlannerState`'s module-level `_plan`/`_hidden` mutable state for any missed-invalidation path.
4. **Unit and encoding correctness.** Check every hour/minute conversion in `js/utils/datetime.js` (`parseExamDate`/`formatExamDate`) for off-by-one or AM/PM boundary errors (particularly the `12 am`→`0` and `12 pm` special cases at lines 49-50 and 72-73) — verify both directions independently rather than trusting the round-trip test alone.
5. **Enumeration and whitelist completeness.** Two enumeration-style checks in scope: (a) `subjects.js`'s `group`/`type` dual-field encoding — extract every `(group, type)` pair actually present in the 27 subject rows and confirm they partition exactly into `('core'|'compulsory', 'Compulsory')` and `('elective', 'Elective')` with zero exceptions (List A: extract from `subjects.js` directly; List B: the two expected pairings); (b) the `data/stats/index.js` registry — list every currently-exported term key and confirm each matches `/^(summer|winter)\d{4}$/` (mechanical check, no `quality/mechanical/` artifact needed per the skill's "don't create an empty directory" rule, since this is a 6-line hand check, not a dispatch-function extraction — but still perform it by reading the file directly, not by trusting `REQUIREMENTS.md`'s or `CONTRACTS.md`'s prose).

**Additional project-specific scrutiny area — Parallel DnD implementation drift:** Explicitly diff `js/ui/ui-board.js`'s `handleDrop` against `js/ui/ui-touch-dnd.js`'s `onPointerUp` line-by-line for behavioral differences beyond the already-documented remove-then-add pattern (CB-1/BUG tracker) — in particular check error handling (`handleDrop` wraps in try/catch and logs on `JSON.parse` failure; `onPointerUp` has no equivalent try/catch around `getDropTarget`/`semesterIdFromContainer` — could a null/malformed target ever throw uncaught there?).

## Pass 2 — Requirement Verification

For each of the 21 requirements in `quality/REQUIREMENTS.md`, verify the code against it individually. Minimum evidence rule: cite at least one `file:line` per requirement; do not group more than 3 requirements under one citation.

Priority order for this codebase (highest-stakes first): REQ-006 (exam-clash scoping — verify the `engine.js:81` guard is exactly what REQUIREMENTS.md describes, not something subtly different), REQ-007/REQ-020 (verify the display-vs-validation divergence is real by tracing `getExamText`'s actual call graph and confirming it truly never calls `parseExamDate`), REQ-012 (verify the `group`/`type` pairing claim against the *current* `subjects.js` contents directly — do not trust CONTRACTS.md's List A/B diff without re-deriving it), REQ-002/REQ-003/REQ-001 (verify `validateSemester`/`addSubject`'s exact rejection conditions), REQ-011 (verify the `17`/`3` graduation thresholds are read as literals, not derived from `subjects.js`'s actual counts — confirm this is intentional per C-018 or flag as a latent drift risk if `subjects.js` is ever restructured to have a different compulsory count).

For REQ-014 (storage resilience), REQ-013 (autosave), and REQ-009 (null-safe clash inputs), a SATISFIED verdict is expected (Phase 1 exploration found no gaps) — Pass 2 should still cite the specific `try/catch` blocks and null-guards individually rather than asserting "storage.js is fine" as a blanket claim.

## Pass 3 — Cross-Requirement Consistency

Compare these specific requirement pairs (all identified during Phase 1/2 exploration as sharing a field, constant, or policy):

- **REQ-005 vs REQ-006** — same function (`getClashingSubjects`), different term-scoping for lecture vs. exam clashes. Is this asymmetry justified anywhere (comment, commit message, README passage)? If not, it's the strongest cross-requirement inconsistency in the codebase.
- **REQ-007 vs REQ-020** — `parseExamDate`'s strict validation vs. `getExamText`'s validation-free display of the same underlying string. Confirm no intermediate layer (e.g. a shared "get display-safe exam string" helper) exists that would resolve this — Phase 1 exploration found none, but Pass 3 should independently verify by grepping for all callers of `subject.exam` across the UI layer.
- **REQ-010/REQ-011 (`type`-based) vs REQ-012 (`group`-based)** — confirm no third code path reads a *third* notion of compulsory/elective (e.g. checking `subject.id` ranges directly) that could introduce a third, independently-drifting source of truth.
- **REQ-002 (max 4 per semester) vs REQ-018 (pool exclusion) vs onboarding's `applyPathway`** — `SUGGESTED_PATHWAY` in `js/data/suggested-pathway.js` places subjects in specific semesters; verify that none of its semester groupings actually exceed 4 subjects (would silently violate REQ-002 via the un-checked `applyPathway` call path — REQ-017's gap) by counting `sem.subjects.length + (sem.electiveSlots || 0)` for every entry in `SUGGESTED_PATHWAY` and confirming it's ≤4 everywhere.

## Source Code Boundary Rule

This review must never modify any file outside `quality/`. All proposed fixes are expressed as patch files under `quality/patches/`.

## Output

Write findings to `quality/code_reviews/pass1-structural.md`, `quality/code_reviews/pass2-requirements.md`, `quality/code_reviews/pass3-consistency.md`. Combine confirmed findings into `quality/BUGS.md` per the BUGS.md conventions in the skill (bug ID, file:line, severity, spec basis, patches).
