## Reconciled findings

### BUG-001 — Exam-clash detection scoped to current term only (`engine.js:81`)

**Verdict: CONFIRMED, 3/3.** Severity: **HIGH** (upgraded from the original REQ-006 Tier-3-gap-with-no-explicit-severity framing).

- Auditor 1: confirmed via fresh source read, no severity opinion given (deferred to human decision on whether the scoping is intentional).
- Auditor 2 (Gemini): confirmed, HIGH — argues there is no plausible legitimate reason to suppress exam-clash warnings for future terms while lecture clashes are checked unconditionally, and that this directly contradicts the multi-year-planning promise in QUALITY.md.
- Auditor 3: confirmed, HIGH — but adds a material, credible countervailing consideration auditor 2 does not raise: `subject.exam` may represent the *currently published* timetable for the current sitting, and reusing that same value to evaluate a *future* semester could produce false-positive clashes against a date that has no bearing on that future term's actual (not-yet-published) exam schedule. This is not a hypothetical — it is exactly the situation now in the repo (every subject's `exam` field is `null` pending the next timetable), which supports auditor 3's caution over auditor 2's stronger "no plausible legitimate reason" framing.

**Reconciliation:** All three confirm the defect exists and rate it HIGH. The disagreement is about *root cause / correct fix shape*, not about whether it's a real gap — auditor 2 treats it as pure omission; auditor 3 correctly identifies that the current-term restriction may be a deliberate (if undocumented) guard against comparing stale/current dates as if they were future ones. This reframes the fix: the correct remedy is not simply "remove the `semesterId === currentTerm` condition" (which could introduce false-positive clashes once future exam dates start getting populated in `subjects.js` ahead of the timetable's actual next-next-term publication), but rather to scope exam-clash checking to *any* semester where the compared subjects both have real, parsed exam dates for that specific term — which the current single-`subjects.js`-array data model doesn't actually support (there's only one `exam` field per subject, not one per term). **This bug is confirmed HIGH, but the writeup's proposed fix needs revision** — see "Fix guidance" below.

### BUG-004 — Markdown export sorts alphabetically, not chronologically (`ui-toolbar.js:26`)

**Reconciliation — resolved against source, not by vote-counting.** This is exactly the kind of contested point the protocol says to verify mechanically rather than split the difference on. I read `js/data/suggested-pathway.js` (`generateTermSequence`), which is the actual function that generates the board's chronological term sequence, and computed both orderings directly:

```
Chronological (board order):  winter2026, summer2026, winter2027, summer2027, winter2028, summer2028, winter2029, summer2029
Alphabetical (export order):  summer2026, summer2027, summer2028, summer2029, winter2026, winter2027, winter2028, winter2029
```

These diverge completely for any plan spanning more than two terms — which is the normal case for this app's core use case (a 20-subject, multi-year progression). This is not a rare edge case Perplexity was right to be cautious about promoting without evidence; it is the default outcome, now directly demonstrated against the real board-order source. **Severity is confirmed HIGH, resolving the split in Gemini's favor with mechanical proof**, and auditor 3's caution (don't assert a fact the excerpts don't establish) is itself validated as the correct instinct — it asked for exactly the evidence that has now settled the question.

### Net-new finding (auditor 3, QUESTION) — Core-order check ignores temporal placement

**Verdict: CONFIRMED as a real gap in the code's behavior; correctly flagged as a QUESTION rather than a BUG against REQ-004 as written.**

Verified directly: `Engine.checkCoreOrder` (`engine.js:44-62`) checks only whether an earlier-sequence core subject exists *anywhere* in the plan (`allPlanned.includes(id)`), never whether it's placed in an earlier *semester*. Placing core subject `03` in `winter2028` while `01`/`02` sit in `winter2029` triggers no warning, despite being temporally backwards. Checked REQ-004's exact wording (`quality/REQUIREMENTS.md`): it explicitly documents "missing from the plan" (presence-only), matching the code as-built — so this is not a violation of the written requirement, it's a real gap between the code's actual behavior and what a reasonable user might expect ("out of order" reasonably implies temporal order, not just presence). **Not added to BUGS.md as a defect against REQ-004**, but recorded as a legitimate specification gap for the maintainer to decide: should "out of order" mean "not yet in the plan" (current behavior) or "not yet in an earlier semester" (stronger, more intuitive guarantee)? This needs a product decision, not a code fix, until that's resolved.

### Net-new finding (auditor 3, QUESTION) — Arbitrary semester IDs are accepted by validation logic

**Verdict: CONFIRMED as a real code characteristic; correctly left as a QUESTION, not promoted to a tracked bug.**

Verified directly: `Engine.isAvailableInTerm` (`engine.js:8-13`) treats any `termId` not containing the substring `'winter'` as `'summer'` — an unrecognized or malformed ID like `'typo'` or `'wintter2027'` silently resolves to `'summer'` rather than being rejected. `PlannerState.getSemester` can also create new plan keys on demand. However, the only caller that supplies `semesterId` values is the board UI, which sources them exclusively from `generateTermSequence()` — always well-formed. **No live exploit path exists today**, matching auditor 3's own caution not to assert a user-facing defect without evidence of reachability. Recorded as a latent robustness gap (LOW) worth a defensive assertion if any future code path ever accepts a semester ID from outside `generateTermSequence`'s output — not urgent, not a tracked bug.

## Fix guidance updates required

**BUG-001's writeup needs revision before a fix patch is written.** The original framing ("just remove the `semesterId === currentTerm` restriction") is not safe given auditor 3's correctly-identified risk: `subjects.js` currently stores one `exam` field per subject, representing only the *current* term's published timetable. Comparing that same value against subjects placed in *future* semesters — which is what an unconditional exam-clash check would do — would produce false-positive clashes once future terms start having real exam dates populated (which won't happen until LPAB publishes each term's timetable in turn). The correct fix needs either: (a) a per-term exam-date model instead of one `exam` field per subject, or (b) exam-clash checking that only activates for a given semester once independently-verified real exam data exists for that specific term (not just non-null). This is now a design decision for the maintainer, not a one-line patch — recommend surfacing this explicitly rather than shipping the originally-proposed diff as-is.
