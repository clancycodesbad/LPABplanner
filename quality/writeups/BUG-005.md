# BUG-005: Drag-and-drop can silently lose a subject on a failed cross-semester move

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-09-26 · Project: LPABplanner

## Summary

Both the native-mouse drag-and-drop path (`ui-board.js:handleDrop`) and the custom touch drag-and-drop path (`ui-touch-dnd.js:onPointerUp`) remove a subject from its source semester **before** attempting to add it to the target semester, and neither checks whether the add succeeds or restores the subject if it fails. A student dragging a subject between two semesters where the target is already full (or, less commonly with current data, term-unavailable) loses that subject from its original slot with no rollback — it silently reverts to the pool, with only an easily-missed error banner as the sole indication anything went wrong.

## Spec reference

No formal spec states a rollback requirement explicitly. The closest documented commitment is README's "Auto-save — Plan is saved to localStorage and persists across page reloads," and the broader implicit promise of a planning tool: actions that don't succeed shouldn't have destructive side effects. A failed "move" silently becoming a "delete" violates that expectation even though no code path explicitly claims otherwise.

## The code

```js
// ui-board.js:215-228 (handleDrop)
function handleDrop(event, targetSemesterId) {
    event.preventDefault();
    try {
        const data = JSON.parse(event.dataTransfer.getData('text/plain'));
        const subject = subjects.find(s => s.id === data.id);
        if (!subject) return;
        if (data.source !== 'pool' && data.source !== targetSemesterId) {
            PlannerState.removeSubject(data.source, data.id); // <-- removed unconditionally
        }
        handleAddSubject(subject, targetSemesterId); // <-- may fail; no check, no rollback
    } catch (err) {
        console.error('Drop failed:', err);
    }
}
```

```js
// ui-touch-dnd.js:123-144 (onPointerUp) — identical pattern
if (target) {
    const targetSemId = semesterIdFromContainer(target);
    if (targetSemId) {
        if (dragState.sourceId !== 'pool' && dragState.sourceId !== targetSemId) {
            PlannerState.removeSubject(dragState.sourceId, dragState.subjectId); // <-- same defect
        }
        handleAddSubject(dragState.subject, targetSemId);
    }
}
```

## Observable consequence

Fill a semester to 4 subjects (the cap). Drag a subject from any other semester onto the full one. The dragged subject disappears from its original slot immediately (the remove happens first); `handleAddSubject` then rejects the add (semester full) and shows an error banner — but the banner only explains *why* the add failed, not that the subject is now nowhere in the plan. The student must notice the subject missing from where they left it and manually re-drag it back from the pool.

## Depth judgment

This defect is confirmed identically present in **both** the mouse and touch drag-and-drop code paths (see EXPLORATION.md's Cross-Implementation Consistency deep dive) — they were written at different times (touch DnD added in later "mobile stage" commits per git log) but share the exact same remove-then-add structure, strongly suggesting the touch implementation was deliberately written to mirror the native one, defect included. A correct fix must be applied to **both** files identically, or the two paths will drift — fixing only `ui-board.js` would leave mobile users (an explicit target of the most recent three commits) still exposed to data loss.

## The fix

Proposed restructuring for `ui-board.js:handleDrop` (validate before removing):

```diff
--- a/js/ui/ui-board.js
+++ b/js/ui/ui-board.js
@@ -213,11 +213,18 @@
 
 function handleDrop(event, targetSemesterId) {
     event.preventDefault();
     try {
         const data = JSON.parse(event.dataTransfer.getData('text/plain'));
         const subject = subjects.find(s => s.id === data.id);
         if (!subject) return;
-        if (data.source !== 'pool' && data.source !== targetSemesterId) {
-            PlannerState.removeSubject(data.source, data.id);
-        }
-        handleAddSubject(subject, targetSemesterId);
+        const isMove = data.source !== 'pool' && data.source !== targetSemesterId;
+        if (isMove) {
+            // Validate against the target BEFORE removing from the source,
+            // so a rejected move never loses the subject.
+            const targetList = PlannerState.getSemester(targetSemesterId);
+            const errors = targetSemesterId === 'completed' ? [] : Engine.validateSemester(targetList, subject, targetSemesterId);
+            if (errors.length > 0) {
+                handleAddSubject(subject, targetSemesterId); // reuse existing error-banner UI, no removal happened
+                return;
+            }
+            PlannerState.removeSubject(data.source, data.id);
+        }
+        handleAddSubject(subject, targetSemesterId);
     } catch (err) {
         console.error('Drop failed:', err);
     }
 }
```

**This diff is a proposal for `ui-board.js` only, not an applied/validated fix.** It has NOT been mechanically validated (no `git apply --check`/worktree compile check was run for this specific diff) because a correct, complete fix must also be written for `ui-touch-dnd.js:onPointerUp` with the identical logic, and reconciling the slightly different code shapes between the two files (different local variable names, different control flow around `target`/`targetSemId`) is a larger change than this run's scope allows to do safely without risking an incomplete or subtly-wrong patch. The maintainer should apply the same "validate against target before removing from source" principle to both files, ideally by extracting a small shared helper (e.g. `attemptMove(subject, sourceId, targetId)`) that both `handleDrop` and `onPointerUp` call, which would also structurally prevent the two paths from drifting again in the future.

`quality/test_regression.mjs`'s `BUG-005` test reproduces the exact remove-then-validate sequence using `Engine.validateSemester` directly and confirms the source list ends up empty after a rejected add, with no code path that restores it.
