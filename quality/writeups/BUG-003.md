# BUG-003: Malformed exam dates display as valid but vanish from clash detection

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-09-26 · Project: LPABplanner

## Summary

`getExamText` (`js/ui/ui-board.js:19-43`), which decides what exam text to show on a subject tile, never validates `subject.exam` through `parseExamDate` — it treats any truthy string as displayable. Meanwhile, `examTimesClash` (used for clash detection) does route the string through `parseExamDate`, and silently treats an unparseable result as "no exam, no clash." A single malformed-but-non-null exam string is therefore shown to the student as if it were a valid date, while being completely invisible to clash detection.

## Spec reference

README.md: "Exam date format is strict — `datetime.js` expects `'D Mon YYYY, H.MM am/pm'`. Do not change this format in `subjects.js` without updating the parser." This establishes that format correctness matters and is expected to be enforced somewhere in the pipeline.

## The code

```js
// ui-board.js:19-43 (getExamText) — never calls parseExamDate
export function getExamText(subject, semesterId) {
    if (semesterId === 'completed') return '';
    const safeTerm = typeof currentTerm !== 'undefined' ? currentTerm : 'winter2026';
    if (semesterId === safeTerm) {
        return subject.exam ? `📝 Exam: ${subject.exam}` : '📝 Exam: TBA'; // <-- raw string, no validation
    }
    // ... historical-archive fallback, also uses raw strings ...
}
```

```js
// datetime.js:85-89 (examTimesClash) — DOES call parseExamDate, silently drops unparseable input
export function examTimesClash(examA, examB) {
    const a = parseExamDate(examA);
    const b = parseExamDate(examB);
    if (!a || !b) return false; // malformed input silently treated as "no clash"
    return a.getTime() === b.getTime();
}
```

Confirmed via `grep -n "parseExamDate" js/ui/*.js engine.js js/state/*.js`: zero matches — `parseExamDate` is called only within `datetime.js` itself.

## Observable consequence

If a future twice-yearly data update introduces a transcription slip (e.g., `'8 Sept 2026, 9.00 am'` instead of `'8 Sep 2026, 9.00 am'` — a highly plausible typo given "Sept" is the more natural English abbreviation), the student sees `📝 Exam: 8 Sept 2026, 9.00 am` on the subject tile — a date that looks entirely legitimate — while that subject is silently excluded from all exam-clash checking. The maintainer gets only a `console.warn` in the browser console, which nobody monitors during normal use. This is confirmed directly: `parseExamDate('8 Sept 2026, 9.00 am')` returns `null` (verified in `quality/test_regression.mjs`'s BUG-003 test).

```diff
-        return subject.exam ? `📝 Exam: ${subject.exam}` : '📝 Exam: TBA';
+        if (!subject.exam) return '📝 Exam: TBA';

```

**This diff is a proposal, not an applied/validated fix.** It addresses only the current-term display branch shown above; the historical-archive fallback branch later in the same function reads exam strings from `archive.js` and would need an equivalent guard for full coverage. It is withheld from `quality/patches/` because the exact wording/styling of the warning is a UX decision better made by the maintainer, and because a full fix should decide whether to also validate at data-load time (catching the problem before it ever reaches display) rather than only at render time.
