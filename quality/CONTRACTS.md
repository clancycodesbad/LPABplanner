Phase A of the requirements pipeline: every behavioral contract observed in the source, listed exhaustively (discovery, not curation). Each feeds one or more requirements in `REQUIREMENTS.md`.

## engine.js

- C-001: `isAvailableInTerm(subject, termId)` returns `true` unconditionally when `termId === 'completed'`.
- C-002: `isAvailableInTerm` derives `'winter'`/`'summer'` from whether `termId` (lowercased) contains `'winter'`; anything not containing `'winter'` is treated as `'summer'`.
- C-003: `isAvailableInTerm` returns whether `subject.terms` (case-insensitively) includes the derived term string.
- C-004: `validateSemester` pushes an error if the subject isn't available in the target term.
- C-005: `validateSemester` pushes an error if the target semester already has 4 or more subjects.
- C-006: `validateSemester` returns an empty array (no errors) when both checks pass.
- C-007: `checkCoreOrder` returns `null` immediately if the subject is not in `CORE_ORDER` or is first in sequence (index ≤ 0, i.e. index -1 or 0).
- C-008: `checkCoreOrder` computes "missing prior" core subjects by checking whether every earlier `CORE_ORDER` ID appears anywhere in the flattened plan (any semester, including `completed`).
- C-009: `checkCoreOrder` returns `null` if no prior core subjects are missing.
- C-010: `checkCoreOrder` returns a warning string naming all missing prerequisite subjects by name (falling back to ID if the subject can't be found) when any are missing.
- C-011: `getClashingSubjects` compares every unordered pair of subjects in a semester list.
- C-012: A lecture clash is recorded (both ways) when two subjects share the exact same `lecture` string.
- C-013: An exam clash is recorded (both ways) via `examTimesClash` **only when** `semesterId === currentTerm`.
- C-014: `getClashingSubjects` deduplicates identical warning strings per subject (checks `.includes()` before pushing).
- C-015: `calculateProgress` flattens all semester arrays (including `completed`) into one list.
- C-016: `calculateProgress` counts subjects whose `type.toLowerCase() === 'compulsory'` and `'elective'` separately.
- C-017: `calculateProgress` returns `readyToGraduate: true` iff `compulsoryCount === 17 && electiveCount >= 3`.
- C-018: `calculateProgress` required counts are hardcoded to 17 (compulsory) and 3 (electives), independent of the actual `subjects.js` contents.

## js/utils/datetime.js

- C-019: `parseExamDate(null|undefined)` returns `null` with no warning (documented as a safe no-op).
- C-020: `parseExamDate` requires the exact pattern `D Mon YYYY, H.MM am/pm` (1–2 digit day, 3-letter month, 4-digit year, 1–2 digit hour, 2-digit minute, am/pm case-insensitive); anything else logs a console warning and returns `null`.
- C-021: `parseExamDate` returns `null` and logs a warning if the month abbreviation isn't recognized (even if the regex otherwise matched — defensive, though the regex's `\w{3}` would already need to be a real 3-letter token).
- C-022: `parseExamDate` converts 12-hour to 24-hour correctly: `pm` and hour ≠ 12 adds 12; `am` and hour === 12 sets hour to 0.
- C-023: `formatExamDate` returns `null` for non-`Date` or invalid-`Date` input.
- C-024: `formatExamDate` converts 24-hour back to 12-hour display, with `0` displayed as `12` and hours `>12` reduced by 12.
- C-025: `examTimesClash(examA, examB)` returns `false` if either input fails to parse (via `parseExamDate`).
- C-026: `examTimesClash` returns `true` iff both parsed times are exactly equal (`getTime()` equality — same date AND time).
- C-027: `sortByExamDate` does not mutate its input array (uses spread before `.sort()`).
- C-028: `sortByExamDate` places subjects with unparseable/absent exam dates at the end, preserving relative order among themselves (stable sort is assumed but not explicitly guaranteed by the comparator returning `0` for two nulls).

## js/state/storage.js

- C-029: Every exported function wraps its `localStorage` access in try/catch and never throws.
- C-030: `loadPlan()` returns `{ completed: [] }` if no stored value exists, parsing fails, or access throws.
- C-031: `loadHiddenSubjects()` returns `[]` on any failure or absence.
- C-032: `clearPlanOnly()` removes only the plan key, leaving hidden-subjects and onboarding-flag keys intact.
- C-033: `clearAll()` removes all three keys (plan, hidden, onboarding).

## js/state/planner-state.js

- C-034: Module-level `_plan`/`_hidden` are initialized once at import time via `loadPlan()`/`loadHiddenSubjects()`.
- C-035: `getSemester(id)` auto-creates (and does NOT immediately persist) an empty array at `_plan[id]` if absent, then returns the (possibly newly-created) array reference.
- C-036: `getClashes(semesterId)` returns `{}` (not an error) if the semester doesn't exist in `_plan`, without mutating `_plan`.
- C-037: `getClashes` defaults `currentTerm` to `'winter2026'` if the imported `currentTerm` is nullish.
- C-038: `addSubject` rejects (returns `{success:false}`) if the subject is already anywhere in the plan (checked via `getProgress().totalSubjectsList`).
- C-039: `addSubject` skips `Engine.validateSemester` entirely when `semesterId === 'completed'` (no max-4 or term-availability check for the completed bucket).
- C-040: `addSubject` calls `savePlan` immediately after a successful push, before checking for a core-order warning.
- C-041: `addSubject` returns `{success:true, warnings:[...]}` when a core-order warning applies, else `{success:true}` alone.
- C-042: `removeSubject` is a silent no-op if the semester doesn't exist; otherwise filters the subject out and saves.
- C-043: `markCompleted` is a silent no-op if the semester doesn't exist or the subject isn't found in it.
- C-044: `markCompleted` splices the subject out of its source semester and pushes it onto `completed`, saving once after the move.
- C-045: `resetPlanOnly` resets `_plan` to `{completed: []}`, calls both `clearPlanOnly()` (removes stored plan key) AND `savePlan(_plan)` (immediately re-writes the reset empty plan) — hidden-subjects storage is untouched.
- C-046: `restoreSubject` removes the given ID from `_hidden` and persists.

## js/services/stats-service.js

- C-047: `effectiveFail(stats)` returns `stats.fail` unchanged if `dns` is absent/zero.
- C-048: `effectiveFail` computes `((failCount + dns) / (sat + dns)) * 100` rounded to 2 decimal places when `dns > 0` and `sat + dns > 0`.
- C-049: `effectiveFail` falls back to `stats.fail` if `sat + dns === 0` even when `dns > 0` (division-by-zero guard).
- C-050: `normalisedBands` maps v1's `merit` field to the returned `credit` field; v1 has no `hd` (always `null`).
- C-051: `normalisedBands` for v2 passes `credit`/`hd` through as-is (nullish-coalesced to `null` if absent).
- C-052: `sortedTerms()` sorts ascending by 4-digit year extracted via regex, then places `summer`-prefixed terms before `winter`-prefixed terms within the same year.
- C-053: `getTermHistoryForSubject` returns only terms where the subject has a stats entry, sorted oldest-first.
- C-054: `getLatestStatsForSubject` returns the last (most recent) entry from `getTermHistoryForSubject`, or `null` if empty.
- C-055: `getHighFailSubjects(threshold=25)` returns subjects whose *latest* effective fail rate is at/above threshold, sorted descending by fail rate.
- C-056: `getDifficultyBand` returns `'high'` (≥30), `'medium'` (≥15), `'low'` (<15), or `null` (no data) based on latest effective fail rate.
- C-057: `getAvailableTerms` returns terms newest-first (reverse of `sortedTerms`).

## js/data/suggested-pathway.js

- C-058: `SUGGESTED_PATHWAY` is a fixed 8-entry array; entries 6–8 (index 5–7) each declare `electiveSlots: 1`.
- C-059: `generateTermSequence(currentTerm)` alternates Winter/Summer starting from `currentTerm`'s season, incrementing the year only on a Summer→Winter transition (i.e. year increments when moving from a summer term to the next winter term).
- C-060: `generateTermSequence` extracts the starting year via a 4-digit regex match, defaulting to `new Date().getFullYear()` if no match.

## js/ui/ui-board.js

- C-061: `getExamText` returns `''` for `semesterId === 'completed'`.
- C-062: `getExamText` shows the live `subject.exam` (or "TBA" if null) when `semesterId === currentTerm` (the "safe" fallback default `'winter2026'` is used if `currentTerm` is undefined).
- C-063: `getExamText` for non-current terms prefers the subject's own (future) `exam` field if set; otherwise searches `historicalExams` newest-term-first for the most recent past sitting.
- C-064: `getExamText` never calls `parseExamDate` — it treats `subject.exam` truthiness alone as "has an exam string," independent of whether that string is well-formed.
- C-065: `handleAddSubject` clears any existing feedback panel state at the start of every call.
- C-066: `handleAddSubject` shows a non-blocking core-order warning banner (if applicable) BEFORE attempting the actual add.
- C-067: `handleAddSubject` shows an error banner (replacing any warning) if `PlannerState.addSubject` fails, and always re-renders board+pool regardless of success/failure.
- C-068: On touch-primary devices, the first error message is also shown as a toast (`isTouchPrimary && result.errors.length > 0`).
- C-069: `renderPlannerBoard` computes `extraSemestersNeeded = Math.ceil(Math.max(20 - progress.totalSubjects, 0) / 3)` and renders terms up to `lastPopulatedIndex + 1 + extraSemestersNeeded` (minimum 1), from a fixed 30-term (`winter2026`..`summer2040`) list.
- C-070: `handleDrop` removes the subject from its source semester (if source ≠ `'pool'` and source ≠ target) BEFORE calling `handleAddSubject` on the target — no rollback if the add fails.
- C-071: `window.removeSubject`/`window.markCompleted` are global functions invoked from inline `onclick=` HTML attributes generated in `createSubjectSlot`.

## js/ui/ui-touch-dnd.js

- C-072: Touch DnD handlers ignore all events where `e.pointerType === 'mouse'` (native DnD handles mouse).
- C-073: `getDropTarget` temporarily hides the ghost element so `elementFromPoint` doesn't detect the ghost itself as the drop target.
- C-074: `semesterIdFromContainer` returns `'completed'` for the completed-slots container, or derives a term ID from the enclosing `.semester-card`'s `<h2>` text via `.replace(' ', '')` (single, non-global replace) + `.toLowerCase()`.
- C-075: `onPointerUp` mirrors `handleDrop`'s remove-then-add sequence with no rollback (same defect surface as C-070).
- C-076: `initTouchDnD` re-attaches handlers idempotently by removing before adding (safe to call after every render).

- C-078: `applyPathway` and the Path B "confirm" handler call `PlannerState.addSubject` in a loop without checking/reporting the returned result.
- C-079: `finishWizard` always calls `markOnboardingDone()` regardless of which path was taken or whether any subjects were actually placed.
- C-080: Path C (`renderSubjectPick`) computes the hidden-subjects list as "every subject ID not checked," defaulting all checkboxes to checked.

## js/ui/ui-toolbar.js

- C-081: `handleExport` always includes a `## Completed` section first (if non-empty), then all other semester keys sorted alphabetically (not chronologically — `'summer2026'` sorts before `'winter2026'` alphabetically, and `'winter2027'` sorts before `'summer2027'`... actually alphabetical sort puts `'summer2026' < 'winter2026'` correctly-ish but is NOT term-chronological in general, e.g. `'summer2030'` < `'winter2029'` alphabetically despite 2029 preceding 2030 chronologically).
- C-082: `handleReset`'s modal requires two explicit clicks (choose an option, then confirm) before any destructive action runs; a backdrop click or Cancel button aborts with no changes.
- C-083: The "full reset" path calls `clearAll()` then reloads the page after a 1-second delay (via `showToast` + `setTimeout`).
- C-084: `showToast` removes any existing toast before creating a new one, and self-removes after 3000ms.
