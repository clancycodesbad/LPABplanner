### BUG-001

- **Source:** Code Review Pass 2 (Requirement Verification) + Pass 3 (Cross-Requirement Consistency)
- **File:** `engine.js:81`
- **Description:** `Engine.getClashingSubjects`'s exam-time clash check only executes when `semesterId === currentTerm`. The lecture-clash check in the same function (lines 72-79) has no such restriction. A student planning subjects into any semester other than the current one gets zero exam-clash protection, even though the underlying exam-time data and the `examTimesClash` function are both fully available and used correctly for the current term.
- **Severity:** HIGH — this defeats the tool's core stated purpose ("detects lecture and exam timetabling clashes") for the majority of planning activity (forward planning is the primary use case per UC-01/UC-02).
- **Minimal reproduction:** Place two subjects with identical `exam` date-times into any semester other than `currentTerm`. No warning appears. Placing the same two subjects into `currentTerm` correctly produces a warning.
- **Expected vs actual:** Expected (per README's undifferentiated "detects... exam clashes" claim and per REQ-005's precedent of unconditional lecture-clash checking): exam clashes flagged in every semester. Actual: only flagged in `currentTerm`.
- **Spec basis:** Code inconsistency (Tier 3) — no external/formal spec exists; the inconsistency is between two branches of the same function, and no comment/commit/README justification for the asymmetry was found (searched `git log -- engine.js` and the file itself).
- **Council note (2026-09-27):** Confirmed 3/3 (in-house, Gemini Pro, external/unconfirmed-identity). Auditor 3 (external) surfaced a material consideration the original writeup missed: `subjects.js` stores only one `exam` field per subject (the current term's published date), so the one-line fix originally sketched in `quality/writeups/BUG-001.md` (drop the `currentTerm` condition) would produce false-positive clashes. That fix was not applied.
- **Maintainer decisions (2026-09-27):** (1) A clash only exists between two exams in the same term's timetable — LPAB assigns exam slots deliberately each term, so dates are never compared across terms. (2) Any term with real exam data gets clash checking. (3) A pair that has shared an exam slot in a published timetable before should be flagged as a *possible* clash, worded and styled distinctly from a confirmed one.
- **Fix applied (2026-09-27):** `Engine.getClashingSubjects` (`engine.js`) now works in two tiers. In the current term, once both subjects have published exam dates, a matching time is a confirmed "Exam clash" (red), and real data overrides any historical signal. Anywhere else — any other term, or the current term before its timetable is published — the pair is flagged with `POSSIBLE_EXAM_CLASH` (amber, the existing advisory style) if they clash in the current published timetable or shared a slot within any single archived term (`Engine.haveClashedHistorically`, reading `archive.js`). `ui-board.js` renders the two tiers with different styling.
- **Related defect found and fixed:** saved plans store a full copy of each subject in localStorage, and `loadPlan` restored those copies unchanged — so a plan saved before a term rollover kept the old term's exam dates (and lecture nights), which would have shown as the new term's dates and fed stale data into clash detection. `planner-state.js` now swaps each saved subject for the live `subjects.js` entry (matched by ID) on load. This was live on the deployed site after the Summer 2027 rollover.
- **Regression tests:** `quality/test_regression.mjs` → six `BUG-001` tests covering each rule above (future-term historical clash, no false signal for a never-clashed pair, confirmed current-term clash, real data overriding history, pre-publication current term, current-term dates never confirmed elsewhere), plus `Saved plans pick up current subject data on load`. `quality/test_functional.mjs`'s REQ-006(d) test was rewritten to assert the new rule instead of documenting the old gap.
- **Closure status:** fixed

### BUG-002

- **Source:** Code Review Pass 2 (Requirement Verification)
- **File:** `js/ui/ui-onboarding.js:157-165` (`applyPathway`), `js/ui/ui-onboarding.js:220-226` (Path B confirm handler)
- **Description:** Both functions call `PlannerState.addSubject(...)` in a loop and discard the returned `{success, errors}` result without inspection. If any placement fails, the student receives zero feedback — the onboarding wizard proceeds to "finish" as if everything succeeded.
- **Severity:** MEDIUM — confirmed to be currently dormant (Pass 1/3 mechanically verified that `SUGGESTED_PATHWAY`'s current data never exceeds the 4-subject-per-semester cap, so Path A cannot currently trigger this), but the code has zero defensive handling for the failure case, and this is "dormant but load-bearing": any future edit to `SUGGESTED_PATHWAY` (a plain hardcoded array with no validation against `engine.js`'s constraints) that exceeds capacity would immediately manifest this defect with no other code changes.
- **Minimal reproduction (constructed, since not reachable with current data):** Call the batch-add pattern used by `applyPathway`/Path B with a subject set that would exceed 4-per-semester or violate term availability; observe no error surfaces anywhere.
- **Expected vs actual:** Expected: consistent with `handleAddSubject`'s existing manual-drag error-surfacing pattern (`ui-board.js:63-77`), any onboarding placement failure should be shown to the student. Actual: silently discarded.
- **Spec basis:** Inferred (Tier 5) — no explicit documentation states this requirement, but it is directly implied by the existing, already-implemented error-surfacing pattern for the identical `addSubject` call used elsewhere in the same codebase.
- **Regression test:** `quality/test_regression.mjs` → `BUG-002: a batch-add loop that captures and checks each result reports every failure`. Now asserts the fixed behavior.
- **Fix applied (2026-09-27):** Both call sites (`applyPathway` and the Path B confirm handler) now capture `addSubject`'s return value, collect any subject names that failed to place, and surface them via `showToast(..., true)` — the same mechanism `ui-toolbar.js` already uses elsewhere in the app, so the UX is consistent rather than novel. Toast text names the failed subjects and tells the student to add them manually from the pool.
- **Closure status:** fixed

### BUG-003

- **Source:** Code Review Pass 1 (Structural Review) + Pass 3 (Cross-Requirement Consistency)
- **File:** `js/ui/ui-board.js:19-43` (`getExamText`) vs. `js/utils/datetime.js:23-34` (`parseExamDate`)
- **Description:** `getExamText` displays `subject.exam` (or a historical archive exam string) directly, based only on truthiness, without ever routing it through `parseExamDate`. Meanwhile, `examTimesClash` (used by clash detection) does route exam strings through `parseExamDate` and silently treats any unparseable result as "no exam" (no clash possible). A malformed-but-non-null exam string (e.g., a transcription slip like `'8 Sept 2026, 9.00 am'` — "Sept" instead of "Sep") is therefore displayed to the student as if it were a perfectly valid date, while being completely invisible to clash detection.
- **Severity:** HIGH (upgraded from MEDIUM-HIGH following council reconciliation — all three spec-audit reviewers independently converged on HIGH). This is a display/safety divergence with real consequences for the twice-yearly hand-maintained data update: a maintainer's single transcription mistake produces a wrong-looking-correct date on screen with zero exam-clash protection for that subject, and no user-facing signal (only a `console.warn` nobody is watching for).
- **Minimal reproduction:** `parseExamDate('8 Sept 2026, 9.00 am')` returns `null` (confirmed — `quality/test_regression.mjs`'s BUG-003 test asserts this directly). The same string, if placed in `subjects.js`, would render via `getExamText` as `📝 Exam: 8 Sept 2026, 9.00 am` (truthy, displayed verbatim) with no warning to the student, while `examTimesClash` would treat it as "no exam" for any comparison.
- **Expected vs actual:** Expected: a malformed exam string should either (a) be caught before the data ships (out of scope for this codebase — no data validation tooling exists), or (b) be visibly flagged in the UI if it makes it into the data. Actual: displayed as if valid, with no visible signal of the parse failure.
- **Spec basis:** README's "Exam date format is strict" statement (Tier 4) combined with the code's own internal contradiction (Tier 3) between the validation layer and the display layer.
- **Regression test:** `quality/test_regression.mjs` → `BUG-003: getExamText's current-term branch flags an unparseable exam string instead of displaying it verbatim`. Now asserts the fixed behavior.
- **Fix applied (2026-09-27):** `getExamText` now calls `parseExamDate` before displaying `subject.exam` in both the current-term branch and the historical-archive fallback branch. An unparseable string in the current term now shows `⚠️ Exam date unrecognized: "..."` instead of the raw string; an unparseable historical string is skipped (falls through to the next available historical term or "TBA") instead of being displayed as if valid.
- **Closure status:** fixed

### BUG-004

- **Source:** Code Review Pass 2 (Requirement Verification) + Pass 3 (Cross-Requirement Consistency)
- **File:** `js/ui/ui-toolbar.js:26` (`handleExport`)
- **Description:** The markdown export sorts semester keys alphabetically (`Object.keys(plan).filter(...).sort()`) rather than chronologically. This produces a non-chronological reading order whenever a plan spans certain year boundaries (e.g., `'summer2030'` sorts before `'winter2029'` alphabetically, despite `winter2029` occurring first in real time). Pass 3 additionally confirmed this **disagrees with the app's own on-screen board ordering**, which IS chronological (`ui-board.js:105-119`'s sequential year-incrementing loop) — so the exported document and the live board can show different orderings for the same plan.
- **Severity:** HIGH (upgraded from MEDIUM following council reconciliation). Never produces incorrect *data* (every semester and subject is still included), but the divergence from the board's own order is not a rare edge case: mechanically verified against `js/data/suggested-pathway.js`'s `generateTermSequence` (the actual board-order source) that for any plan spanning more than two terms — the normal case for this app's 20-subject, multi-year use case — the export groups all Summers before all Winters, unrelated to the real sequence. This settled a severity split among the spec-audit council (Gemini: HIGH: "functionally ruins the deliverable"; external auditor: LOW, pending board-order proof) — the mechanical check resolves it in favor of HIGH.
- **Minimal reproduction:** A plan containing `winter2029` and `summer2030` exports with `summer2030` listed before `winter2029`, while the board itself would render `winter2029` before `summer2030`.
- **Expected vs actual:** Expected: chronological order matching the board. Actual: alphabetical order.
- **Spec basis:** README's "Markdown export — One-click copy of the full plan" (Tier 4) combined with the app's own board-ordering behavior as an internal consistency baseline (Tier 3).
- **Regression test:** `quality/test_regression.mjs` → `BUG-004: export ordering now matches chronological order across year boundaries`. `quality/test_functional.mjs`'s duplicate coverage (Export ordering, REQ-021c) updated identically. Both assert the fixed behavior.
- **Fix applied (2026-09-27):** `ui-toolbar.js:handleExport` now sorts via a new `compareTermsChronologically` comparator (year × 10 + season rank, summer before winter within a year) instead of the plain alphabetical `.sort()`, matching `js/data/suggested-pathway.js`'s `generateTermSequence` — the same source the board itself uses to order semesters.
- **Closure status:** fixed (TDD-verified fix patch from `quality/patches/BUG-004-fix.patch` applied to source, matching the mechanically-validated logic)

### BUG-005

- **Source:** Code Review Pass 1 (Structural Review), corroborated by the Cross-Implementation Consistency pattern deep dive (Phase 1)
- **File:** `js/ui/ui-board.js:215-228` (`handleDrop`), `js/ui/ui-touch-dnd.js:123-144` (`onPointerUp`)
- **Description:** Both the native-mouse and touch drag-and-drop implementations remove a subject from its source semester **before** attempting to add it to the target semester, with no check of the add's success and no rollback. If the target add fails (semester full, or, less likely given current data, a term-availability mismatch), the subject has already been removed from its original slot and is not restored anywhere — it silently reverts to the subject pool with only an easily-missed error banner as the only indication.
- **Severity:** HIGH — silent data loss (a subject the student placed and believed was saved simply disappears from its slot) is the single worst failure class for a planning tool whose entire value proposition is trustworthy persistence.
- **Minimal reproduction:** Fill a semester to 4 subjects. Drag a subject from a *different* semester onto the full one. The dragged subject vanishes from its original semester; an error banner appears (easily missed) stating the semester is full; the subject is NOT restored to its original slot.
- **Expected vs actual:** Expected: either the add is validated before the remove happens (preventing the loss entirely), or a failed add restores the subject to its original semester. Actual: unconditional remove-then-add with no rollback.
- **Spec basis:** Inferred (Tier 5) — no explicit documentation states a rollback requirement, but it follows directly from REQ-013's autosave/persistence guarantee ("every successful mutation persists... so I never lose my planning work") — a failed mutation silently causing a *different*, unintended mutation (the removal) directly undermines that guarantee's spirit.
- **Regression test:** `quality/test_regression.mjs` → `BUG-005: a rejected move leaves the subject in its original source semester`. Now asserts the fixed behavior.
- **Fix applied (2026-09-27):** Extracted a shared `attemptMove(subject, sourceId, targetId)` helper in `ui-board.js` (exported), used by **both** `handleDrop` (mouse) and `onPointerUp` (touch, via `ui-touch-dnd.js`'s import). It validates the target with `Engine.validateSemester` *before* removing from the source; a rejected move never removes anything and reuses `handleAddSubject`'s existing error-banner/toast UI to explain why. This directly addresses the Cross-Implementation Consistency risk noted in EXPLORATION.md by making both paths call one function instead of maintaining parallel logic that could drift again.
- **Closure status:** fixed
