# Integration Test Protocol

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-09-26 · Project: LPABplanner

## Working Directory

All commands run from the project root (`C:\Dev\LPABplanner`) using relative paths.

## Safety Constraints

This is a client-only static app with no external services, no network calls, and no destructive server-side operations. The only "safety" concern is **not modifying files outside `quality/`** during test execution, and not leaving stray `localStorage` state in a shared browser profile if these are ever run against a real browser session (use a fresh/incognito profile or a fresh Playwright browser context per run).

## Pre-flight Checks

1. Confirm `index.html` opens correctly when served over HTTP (native ES module imports fail on `file://`): `python3 -m http.server 8080` (or `npx serve .`) from the project root, then load `http://localhost:8080`.
2. Confirm `node --test quality/test_functional.mjs` exits 0 (the Node-level pure-logic suite) before running any DOM-dependent group — a failure at the pure-logic layer should block integration testing, since the UI layer depends on `Engine`/`PlannerState` being correct.

## Why This Protocol Is Manual/Playwright-Oriented, Not Fully Scripted

This project has no test framework, no `package.json`, and no bundler. The functional-test layer (`quality/test_functional.mjs`) covers every pure-logic requirement executable under Node. The requirements below are DOM-dependent (they require rendering `index.html`, simulating drag-and-drop, or reading computed styles) and cannot run under Node's `node:test` without introducing a DOM shim dependency — which would violate the "no heavy new dependencies" guardrail for this run. This protocol documents the exact manual verification steps (usable directly, or automatable later with Playwright per the project's own `webapp-testing` skill if the maintainer chooses to add it) rather than fabricating an execution that didn't happen.

## Execution UX

1. **Plan:** Print the 15 groups + 2 infrastructure checks as a numbered table before running anything (as above).
2. **Progress:** As each group runs, print one line: `✓ Group N — <name>` (pass), `✗ Group N — <name>: <what failed>` (fail), `⧗ Group N — <name>` (in progress).
3. **Summary:** A final pass/fail count table plus a recommendation (`SHIP` / `FIX BEFORE MERGE` / `BLOCK`), written to `quality/results/integration-results.json` per the sidecar schema.
