## Domain and Stack

LPABplanner is a client-only, zero-build static web app: plain HTML5, CSS3, and browser-native ES6 modules (no bundler, no npm, no `package.json`, no test framework). It is a drag-and-drop course-progression planner for the NSW Legal Profession Admission Board (LPAB) Diploma in Law. It has no backend and no network calls; all persistence is via `localStorage`. It must be served over HTTP (not opened as `file://`) because of native ES module imports.

Domain: the Diploma in Law has 20 required subjects — 11 "core" subjects (must be taken in a fixed sequence, IDs `01`–`11`), 6 further "compulsory" subjects (any order, IDs `12`,`13`,`14`,`15`,`17`,`24`), and a pool of 10 "elective" subjects of which exactly 3 must be chosen. Subjects run in `Winter` and/or `Summer` semesters (or both). Each subject has a weekly lecture night and an exam date/time; the tool must warn on lecture-night clashes and exact exam-time clashes within the same semester.

## Architecture

- `index.html` — entry point; loads `js/ui/ui-main.js` as an ES module; inline `<script>` handles dark/light theme toggle only.
- `subjects.js` — canonical subject list + `currentTerm` constant. No imports.
- `archive.js` — historical exam dates keyed by term, used as a "last known exam date" fallback for past terms not in `data/stats`. No imports.
- `engine.js` — pure validation/business-rule module (`Engine` object): `isAvailableInTerm`, `validateSemester`, `checkCoreOrder`, `getClashingSubjects`, `calculateProgress`. Imports `datetime.js` and `subjects.js`.
- `planner.js` — backwards-compat re-export shim for `PlannerState` (re-exports `js/state/planner-state.js`).
- `js/state/storage.js` — sole localStorage read/write boundary. Exports `hasExistingPlan`, `loadPlan`, `savePlan`, `loadHiddenSubjects`, `saveHiddenSubjects`, `markOnboardingDone`, `isOnboardingDone`, `clearAll`, `clearPlanOnly`. Every localStorage call is wrapped in try/catch.
- `js/state/planner-state.js` — in-memory plan state singleton (`_plan`, `_hidden` module-level variables, loaded once at import time). `PlannerState.addSubject/removeSubject/markCompleted/resetPlanOnly/getPlan/getSemester/getClashes/getProgress/getHidden/setHidden/restoreSubject/loadData/saveData`.
- `js/utils/datetime.js` — exam-date-string parsing (`parseExamDate`), formatting (`formatExamDate`), equality-based clash check (`examTimesClash`), and sort (`sortByExamDate`). Regex-based parser for the strict format `'D Mon YYYY, H.MM am/pm'`.
- `js/data/suggested-pathway.js` — hardcoded 8-semester LPAB-recommended sequence (`SUGGESTED_PATHWAY`) and `generateTermSequence(currentTerm)` which alternates winter/summer starting from the app's current term.
- `js/services/stats-service.js` — pure lookup/derivation layer over `data/stats/*.js` (historical exam pass/fail statistics by term). Computes `effectiveFail` (DNS-adjusted fail rate), `normalisedBands` (v1→v2 grading-scheme mapping), `getDifficultyBand`, `getHighFailSubjects`, term sorting.
- `data/stats/index.js` + `data/stats/{term}.js` — per-term statistics data files (summer2023, winter2023, summer2024, winter2024, winter2025, summer2026). Comment states "summer = March sitting, winter = July/Aug sitting" — i.e. within a calendar year Summer precedes Winter.
- `js/ui/ui-main.js` — app bootstrap; wires `PlannerState.loadData()`, initial render, export button, onboarding gate, help button. Exports `feedbackPanel`/`errorListEl` DOM refs consumed by `ui-board.js` (a circular-ish coupling: `ui-board.js` imports from `ui-main.js`, and `ui-main.js` imports `renderPlannerBoard`/`renderSubjectPool` from `ui-board.js`/`ui-pool.js`).
- `js/ui/ui-board.js` — renders semester cards/slots, handles native HTML5 drag-and-drop (`ondragstart`/`ondrop`), `handleAddSubject`, `handleDrop`, exposes `window.removeSubject`/`window.markCompleted` as global functions consumed by inline `onclick=` handlers in generated HTML.
- `js/ui/ui-pool.js` — renders the left-hand subject pool sidebar, including a collapsible "hidden subjects" section with per-item Restore buttons.
- `js/ui/ui-progress.js` — renders progress bars/graduation status text from `PlannerState.getProgress()`.
- `js/ui/ui-toolbar.js` — export-to-markdown (clipboard), print, and the two-step reset modal (`showResetModal`); exports `showToast`.
- `js/ui/ui-onboarding.js` — two independent flows: first-run setup wizard (paths A/B/C) and a separate repeatable "Help/Tour" overlay.
- `js/ui/ui-touch-dnd.js` — custom pointer-event-based drag-and-drop reimplementation for touch/pen input (native HTML5 DnD does not fire reliably on touch), parallel to the native DnD path in `ui-board.js`/`ui-pool.js`.
- `js/ui/ui-stats.js` — pure DOM-building helpers (`createDifficultyBadge`, `createGradeBar`, `createHistoryTable`) consuming `stats-service.js`; renders into pool items and board slots.
- `css/planner.css` — all styling, light/dark tokens via `[data-theme]`, touch-action rules, focus-visible outlines (only found for `.ob-path-btn`).
- `html file version/LPABPlannerApp.html` — explicitly out-of-scope stale snapshot per README ("Do not read or modify... unless explicitly instructed"). Excluded from this audit.

**Data flow:** `subjects.js` (static data) → `PlannerState` (mutations, delegates validation to `Engine`) → `storage.js` (persistence) ⇄ UI modules (render + DOM event wiring) → user drag/drop or button click → `PlannerState` mutation → re-render.

**Most complex module:** `js/ui/ui-board.js` (rendering, native DnD, clash display, semester-list generation with unbounded-looking term generation loop).
**Most fragile module:** `js/ui/ui-touch-dnd.js` combined with `ui-board.js`'s native DnD — two independently maintained, not-obviously-synchronized code paths implementing the same "move a subject between pool/semester/completed" operation (see Pattern Deep Dive: Cross-Implementation Consistency below).

## Open Exploration Findings

At least 8 concrete, file:line-cited findings from domain-driven investigation, spanning 6 different modules:

1. **`js/ui/ui-board.js:215-228` (`handleDrop`) removes the subject from its source semester unconditionally before validating the add at the target.** `handleDrop` calls `PlannerState.removeSubject(data.source, data.id)` whenever `data.source !== 'pool' && data.source !== targetSemesterId`, then calls `handleAddSubject(subject, targetSemesterId)`. `handleAddSubject` → `PlannerState.addSubject` can fail (semester full — max 4 per `engine.js:23-25`, or term mismatch per `engine.js:18-21`). On failure, the subject has already been removed from its original semester but was never re-added anywhere — it silently disappears from the plan and reappears only in the subject pool (not restored to its original slot). The user only sees an error banner; there is no indication the subject was moved out of its prior semester. Same defect independently exists in `js/ui/ui-touch-dnd.js:130-141` (`onPointerUp`) — see Pattern Deep Dive #1 below.
2. **`js/services/stats-service.js:50-57` (`effectiveFail`) can silently divide by zero avoidance but still trust `stats.fail` as a fallback that may itself be `undefined`.** If `dns` is `0`/absent, the function returns `stats.fail` directly (line 52) — if a stats record is missing the `fail` key entirely (a plausible data-entry omission across 6 hand-maintained term files), this returns `undefined`, which then flows into `.toFixed()` calls in `ui-stats.js:43,99,118,168` and would throw `TypeError: undefined is not a function` inside a `forEach` during pool/board rendering, crashing the whole render for every subject after it in iteration order.
3. **`js/utils/datetime.js:23-34` (`parseExamDate`) regex requires exactly one space between comma and time**, but permits variable leading/no leading zero on day/hour. If any future term's data entry uses a slightly different format (e.g., double space, en-dash, or a "TBC" placeholder that isn't literally `null`), the function logs a console warning and returns `null` — swallowed silently in the UI layer (`getExamText` in `ui-board.js:19-43` shows "Exam: TBA" without surfacing that a parse failure occurred, indistinguishable from a legitimately-absent exam).
4. **`js/ui/ui-onboarding.js:157-165` (`applyPathway`) and `js/ui/ui-onboarding.js:220-226` (Path B confirm) silently ignore `PlannerState.addSubject` failures.** Both call `PlannerState.addSubject(termId, subject)` / `PlannerState.addSubject('completed', subject)` in a loop without checking the returned `{success, errors}` object. If `SUGGESTED_PATHWAY` (in `js/data/suggested-pathway.js`) ever places more than 4 subjects in one semester, or a subject unavailable in that generated term (e.g., an elective offered only in Summer landing in a generated Winter term via `generateTermSequence`), the add is dropped with zero user-facing feedback — the user finishes onboarding believing subjects were placed that were not.
5. **`engine.js:64-92` (`getClashingSubjects`) only runs the exam-clash check when `semesterId === currentTerm` (line 81)**, meaning exam-time clashes are detected only for the single "current" term, never for future planned semesters even though those semesters display an exam date/time from the same `subjects.js` data (`ui-board.js:23-25`, `getExamText`). A student planning two clashing subjects in `winter2027` (a future term relative to `currentTerm = 'winter2026'`) gets no clash warning at all, even though the same subjects would clash if planned for the current term. This is a plausible, currently-live discrepancy between what the UI implies ("Clash detection... detects... exam time" per README) and what the engine actually checks.
6. **`js/ui/ui-board.js:102-119` semester-card generation logic caps `allTerms` at a hardcoded 15-year loop (`for (let i = 0; i < 15; i++)`) starting from a hardcoded `year = 2026` (line 106), independent of `currentTerm` from `subjects.js`.** If `subjects.js`'s `currentTerm` is ever updated to a year beyond 2040 (15 years from the hardcoded start), `termsToRender` (line 119) could compute an index beyond `allTerms.length`, and `allTerms.slice(0, N)` where `N > allTerms.length` silently returns a truncated/empty array rather than erroring — semesters the student has already populated beyond year 2040 would stop being rendered on the board (though their data remains in `localStorage`), effectively hiding part of the plan without any error.
7. **`js/ui/ui-touch-dnd.js:59-68` (`semesterIdFromContainer`) derives the semester ID by reading `<h2>` text content and doing `.replace(' ', '')`** — `String.prototype.replace` with a string (not global regex) argument only replaces the **first** occurrence. The heading text is generated in `ui-board.js:127` as `semesterId.replace('winter','Winter ').replace('summer','Summer ')`, producing exactly one space (e.g., "Winter 2026"), so today this round-trips correctly. But it is a latent fragility: any future heading format change (e.g., adding a subject-count suffix like "Winter 2026 (3/4)") would silently break touch drag-and-drop's target detection with no error — drops would just be silently ignored (the `if (targetSemId)` guard at `ui-touch-dnd.js:134` would receive a garbled ID that doesn't match any real semester key, and `PlannerState.getSemester` would then create a bogus new semester key in the plan object via its auto-initializing `if (!_plan[id]) _plan[id] = []` at `planner-state.js:29`).
8. **`js/state/planner-state.js:28-31` (`getSemester`) auto-creates and persists a new empty array key in `_plan` for ANY string passed to it**, including from unsanitized/garbled call sites (see finding 7). Because `getClashes` (`planner-state.js:33-37`) also calls `if (!_plan[semesterId]) return {}` (a read-only guard) but `getSemester` has no such guard and mutates `_plan` on every call, calling `getSemester` with a typo'd or malformed semester ID permanently pollutes the persisted plan object in `localStorage` with a garbage key that will never be cleaned up (not visible in the UI since `renderPlannerBoard` only iterates the fixed `allTerms` array, so the garbage key becomes permanently-orphaned dead data, invisible until someone inspects localStorage directly, but it is exported unfiltered by `js/ui/ui-toolbar.js:26` `Object.keys(plan).filter(k => k !== 'completed').sort()` — a garbage key WOULD show up in the markdown export as a bogus semester heading with subjects under it).
9. **`js/services/stats-service.js:27-35` (`sortedTerms`) assumes every key in `allStats` matches `/\d{4}/` and starts with either `'summer'` or `'winter'`.** `data/stats/index.js` is a hand-maintained registry where semesters are added by uncommenting an export line (per its own header comment) — a future maintainer adding a mistyped export (e.g. a stray key not matching the naming convention) would throw inside `.match(/\d{4}/)[0]` (line 29/30, no null-guard on `.match()` returning `null`) the very first time any stats-consuming UI element renders (`ui-stats.js` `createDifficultyBadge`/`createGradeBar` called from every pool item and board slot), crashing the entire pool/board render — a single bad hand-edit in a leaf data file takes down the whole app.
10. **`css/planner.css`/`index.html` — no keyboard-operable way to add a subject to a semester.** The only mechanism to move a subject from the pool into a semester (or between semesters) is native HTML5 drag-and-drop (mouse) or the custom pointer-based touch DnD (`ui-touch-dnd.js`). There is no click/keyboard equivalent ("click subject, then click target semester", or similar) anywhere in `ui-pool.js`/`ui-board.js`. Removal (`✕ Remove`) and completion (`✓ Done`) do have click-activated buttons, but *adding* a subject to a plan for the first time is drag-only. This is a functional/accessibility gap: a keyboard-only user cannot build a plan at all.

## Quality Risks

At least 5 domain-driven failure scenarios, ranked by priority, each naming a specific function/file/line and a plausible real-world failure mechanism:

1. **[HIGHEST] Silent data loss on invalid subject moves between semesters — `js/ui/ui-board.js:215-228` (`handleDrop`) and `js/ui/ui-touch-dnd.js:123-144` (`onPointerUp`).** Because a drag-and-drop planner's entire value proposition is "let the student freely rearrange subjects across many semesters," the single most common user action after initial setup is dragging a subject from one already-planned semester to another (e.g., rebalancing a semester that's become too full, or moving a subject earlier/later). Domain knowledge about drag-and-drop UIs: the "remove-then-add" pattern without a rollback path is one of the single most common defects in these systems, because unlike most form submissions, a DnD drop has no natural "cancel and revert" gesture the user can retry — the source slot is already gone visually. A student who drags Torts (`03`) from a semester that already has 4 subjects into a semester that already has 4 subjects (an easy mistake to make once a plan is dense) loses Torts from their plan entirely, with no error dialog blocking the action from happening (only an after-the-fact error banner, easily missed) and no visible warning that the subject reverted to the pool rather than staying where it was. This is exactly the kind of "correct-looking but silently wrong" outcome the domain-risk framing calls out: the render completes successfully, no exception is thrown, and the subject simply vanishes from its old slot.
2. **[HIGH] Exam-clash detection has a scope hole for all non-current terms — `engine.js:64-92`, specifically the guard at line 81 (`if (semesterId === currentTerm && examTimesClash(...))`).** Domain knowledge about scheduling/clash-detection tools: the entire reason a clash detector exists is to protect a student from an unrecoverable outcome (missing/double-booking an exam) discovered only once it's too late to change enrollment. A planner that only checks exam clashes for the term chosen as "current" is providing a false sense of security for every other term the student plans ahead — which, given this app's core selling point is "map out your entire progression years in advance," is the majority of planning activity. A student who front-loads two semesters' worth of subject placements (a realistic, encouraged usage pattern — the onboarding wizard's Path A does exactly this via `applyPathway`) gets zero exam-clash warnings for any semester except the very next one, even though the exam-time data exists and the clash-check function is fully capable of running against it.
3. **[HIGH] A single malformed exam-date string is swallowed into an indistinguishable "TBA" display, hiding future data-entry mistakes — `js/utils/datetime.js:23-34` (`parseExamDate`) + `js/ui/ui-board.js:19-43` (`getExamText`).** Domain knowledge about hand-maintained, semester-by-semester data files (this project is explicitly designed to be updated twice a year per the README's "Updating for a New Semester" section, by presumably non-programmer maintainers copying from a PDF): the single highest-probability recurring failure mode is a transcription error in the strict `'D Mon YYYY, H.MM am/pm'` format (extra/missing space, `am`/`pm` capitalization inconsistency the regex actually does tolerate via `/i`, but a stray period, en-dash instead of comma, or "TBC" text would not parse). Because `parseExamDate` only `console.warn`s and returns `null`, and `getExamText` renders exactly the same "📝 Exam: TBA" UI for a genuinely-absent exam (`exam: null` intentionally set, per README's own instructions for subjects "not offered") as for a exam string that failed to parse, a maintainer who fat-fingers next semester's exam-date PDF transcription gets no visible signal in the running app that anything is wrong — only a browser console warning nobody but a developer would see, and only if they had devtools open at exactly the right time.
4. **[MEDIUM-HIGH] `stats-service.js`'s registry-driven design (`data/stats/index.js`) has no defensive validation against its own documented extension procedure — `js/services/stats-service.js:27-35` (`sortedTerms`) and `js/data/... /stats/index.js`.** Domain knowledge about "registry pattern" data modules maintained by uncommenting export lines (the file's own header comment describes exactly this workflow: "Uncomment or add one export line below"): this pattern is inherently error-prone because the person performing the twice-yearly update is following a copy-paste procedure under time pressure (right after a new LPAB timetable PDF is released) and is the same audience likely to make a typo in a term key (e.g. `summer2027` vs `Summer2027` vs `summer_2027`). `sortedTerms()` calls `a.match(/\d{4}/)[0]` with no null-check on `.match()`'s return value and no validation that keys start with `summer`/`winter` — a single malformed export key added to `data/stats/index.js` throws an uncaught `TypeError` the moment any pool item or board slot tries to render a stats badge, which is *every* render after the app loads (via `initTouchDnD`/`renderSubjectPool`/`renderPlannerBoard` calling `createDifficultyBadge`/`createGradeBar` on every visible subject) — turning one bad data-entry keystroke into a fully broken app for every user, not a degraded feature.
5. **[MEDIUM] The 15-year hardcoded semester-generation window is silently finite and untied to the actual `currentTerm` — `js/ui/ui-board.js:105-111`.** Domain knowledge about apps that generate a rolling window of future time periods: hardcoding a start year (`2026`) independently of the single source of truth for "now" (`subjects.js`'s `currentTerm`) is a classic drift bug — the two will only coincidentally agree, and every semester the app is *not* updated (this is a community-maintained hobby tool, likely to lag behind real-world updates during any gap in maintainer availability) the safety margin between the hardcoded `2026` start and the real current year shrinks. Once `currentTerm` drifts far enough past `2026 + i` for any planned term to fall outside the generated 30-term (15 winter + 15 summer) window, `termsToRender` in `renderPlannerBoard` (line 119) would stop rendering that semester's card even though the data still exists in `localStorage` and is still counted in `PlannerState.getProgress()` — the student's completed/graduation math stays correct, but part of their visual plan silently disappears from the board.

## Pattern Deep Dive — Cross-Implementation Consistency

**Target:** `js/ui/ui-board.js`'s `handleDrop` (native mouse DnD, lines 215-228) vs. `js/ui/ui-touch-dnd.js`'s `onPointerUp` (touch DnD, lines 123-144). Both implement the same conceptual operation: "the user has dropped subject X, previously at source S, onto target T."

**Native DnD path** (`ui-board.js:215-228`):
```js
function handleDrop(event, targetSemesterId) {
    event.preventDefault();
    try {
        const data = JSON.parse(event.dataTransfer.getData('text/plain'));
        const subject = subjects.find(s => s.id === data.id);
        if (!subject) return;
        if (data.source !== 'pool' && data.source !== targetSemesterId) {
            PlannerState.removeSubject(data.source, data.id);
        }
        handleAddSubject(subject, targetSemesterId);
    } catch (err) {
        console.error('Drop failed:', err);
    }
}
```

**Touch DnD path** (`ui-touch-dnd.js:123-144`):
```js
function onPointerUp(e) {
    if (!dragState || e.pointerType === 'mouse') return;
    hideGhost();
    clearHighlight();
    dragState.originEl.classList.remove('touch-dragging');
    const target = getDropTarget(e.clientX, e.clientY);
    if (target) {
        const targetSemId = semesterIdFromContainer(target);
        if (targetSemId) {
            if (dragState.sourceId !== 'pool' && dragState.sourceId !== targetSemId) {
                PlannerState.removeSubject(dragState.sourceId, dragState.subjectId);
            }
            handleAddSubject(dragState.subject, targetSemId);
        }
    }
    dragState = null;
}
```

**Consistency finding:** The two implementations are structurally near-identical — both do "if source differs from target and source isn't 'pool', remove-then-add" — which is *good* evidence the touch path was deliberately written to mirror the native path (confirmed by the git log: touch DnD was added in "mobile stage 1/2/3" commits on top of a pre-existing native DnD implementation). However, both paths share the exact same defect identified in Open Exploration Finding #1 (remove-before-validate, no rollback on add failure) — this is not a *divergence* bug, but it means **any future fix to one path (e.g., adding a rollback-on-failure guard) must be manually mirrored in the other, and there is no shared helper function enforcing that.** A maintainer who fixes `handleDrop` in `ui-board.js` without knowing `onPointerUp` in `ui-touch-dnd.js` duplicates the same logic will silently leave the touch path (mobile users — an explicit target of the last three commits) still broken. This is exactly the "parity gap that will reappear on the next edit" risk the pattern is designed to surface, and it strengthens (rather than independently discovers) Quality Risk #1 — recorded as a **process/maintainability risk**, not a distinct behavioral bug, and folded into the same candidate-bug entry (see Candidate Bugs list, CB-1).

**Secondary finding — drop-target resolution differs subtly:** the native path trusts `targetSemesterId` as passed directly by the DOM `ondrop` handler wiring (`ui-board.js:134`: `slotsContainer.ondrop = (e) => { ...; handleDrop(e, semesterId); }` — `semesterId` is a closure variable bound at render time, always a real, valid semester key). The touch path instead re-derives the target ID at drop time by *string-parsing DOM text* via `semesterIdFromContainer` (`ui-touch-dnd.js:59-68`), which is a strictly weaker, string-parsing-dependent mechanism for what should be the same trusted value — see Open Exploration Finding #7 for the concrete fragility this introduces. The native path has no equivalent fragility because it never needs to re-derive the ID from rendered text. This is a genuine asymmetry between the two "same contract" implementations, not just a duplicated-logic risk, and is tracked as its own candidate bug (CB-4).

## Pattern Deep Dive — Fallback and Degradation Path Parity

**Target:** `js/utils/datetime.js`'s `parseExamDate` (lines 23-34) as the primary path, and its two downstream consumers' degradation behavior on parse failure: `js/ui/ui-board.js`'s `getExamText` (lines 19-43) and `engine.js`'s `examTimesClash` caller chain (via `getClashingSubjects`, lines 64-92).

**Primary path:** `parseExamDate(examString)` either returns a valid `Date` or `null` (on missing input OR on regex-match failure OR on unrecognized month abbreviation), logging a `console.warn` only in the two failure-to-parse branches (not the "no input" branch, which is silent by design per the file's own header comment: "treat null/undefined input as a safe no-op").

**Degradation path 1 — `getExamText` (`ui-board.js:19-43`):** When `subject.exam` is falsy (either genuinely `null` per data, OR — this is the gap — impossible to distinguish from a corrupted string that a caller upstream already discarded, since `getExamText` only ever receives the *original string*, never the parse result) the function falls through to a "last known" lookup in `historicalExams`, and if that also comes up empty, renders `'📝 Exam: TBA'`. Crucially, `getExamText` **never calls `parseExamDate` at all** — it works directly off the raw `subject.exam` string for display purposes. This means a malformed-but-non-null exam string (e.g. `'8 Sept 2026, 9.00 am'` — "Sept" instead of "Sep", a very plausible transcription variant) is displayed to the user *verbatim* as if it were a valid, informative exam time ("📝 Exam: 8 Sept 2026, 9.00 am") — the user sees what looks like a real date — while simultaneously being invisible to `examTimesClash` (which routes the same string through `parseExamDate`, silently gets `null` back, and treats it as "no exam" for clash-detection purposes per `datetime.js:85-89`: `if (!a || !b) return false;`). **This is a genuine fallback/degradation parity bug**, distinct from Quality Risk #3's "indistinguishable TBA" framing: the *display* path and the *clash-detection* path degrade differently on the exact same malformed input — display shows a (wrong-looking-fine) date, clash-detection silently treats it as absent — so a malformed exam date can simultaneously (a) look correct to the student and (b) fail to be checked for clashes at all. Recorded as candidate bug CB-2.

**Degradation path 2 — exam-clash scope (`engine.js:81`):** Already covered in depth as Quality Risk #2 / Open Exploration Finding #5 — the "degradation" here is that the clash-detection contract silently narrows from "all semesters with exam data" to "only the current term," with no signal to the caller or user that coverage dropped. Cross-referencing against Finding #5 confirms this is a real, load-bearing gap: `getExamText` (the display function) computes exam text for **every** semester regardless of whether it equals `currentTerm` (there's no term-based branching there beyond current-vs-not for display *label*, not for *whether an exam field exists*), yet `getClashingSubjects` only evaluates the exam-clash half of its check when `semesterId === currentTerm`. The lecture-clash half of the same function (`engine.js:72-79`) has no such term restriction — it runs for every semester unconditionally. This asymmetry within a *single* function (lecture clashes checked everywhere, exam clashes checked only for one term) is a strong signal of an unintentional gap rather than a deliberate design choice, reinforcing Quality Risk #2's priority.

## Pattern Deep Dive — Enumeration and Representation Completeness

**Target:** the `group` (`'core'|'compulsory'|'elective'`) vs. legacy `type` (`'Compulsory'|'Elective'`) dual-field representation on every subject object in `subjects.js`, and the group→CSS-class / group→label mapping logic duplicated across `js/ui/ui-board.js` and `js/ui/ui-pool.js`.

**List A — actual mapping logic sites (extracted from code):**
- `ui-board.js:155-158` (`createSubjectSlot`): `const sType = subject.type.toLowerCase(); const groupClass = subject.group === 'core' ? 'slot--core' : sType === 'compulsory' ? 'slot--compulsory' : 'slot--elective';`
- `ui-board.js:191-192` (`createSubjectSlot`, label): `const groupLabel = subject.group === 'core' ? 'Core' : subject.group === 'compulsory' ? 'Compulsory' : 'Elective';`
- `ui-pool.js:54-57` (`createPoolItem`): identical structure to `ui-board.js:155-158`, independently written (`const sType = subject.type.toLowerCase(); const groupClass = subject.group === 'core' ? 'pool-item--core' : ...`).
- `ui-pool.js:78-79` (`createPoolItem`, label): identical structure to `ui-board.js:191-192`.
- `engine.js:98-99` (`calculateProgress`): uses `type` exclusively (`s.type.toLowerCase() === 'compulsory'` / `'elective'`), **never reads `group` at all** — meaning `engine.js`'s graduation-progress math has a completely independent notion of "compulsory vs elective" from the `group`-based UI styling/labeling logic.

**List B — what the data actually contains (from `subjects.js`):** every one of the 11 `core` subjects has `group: 'core', type: 'Compulsory'`; every one of the 6 non-core compulsory subjects has `group: 'compulsory', type: 'Compulsory'`; every one of the 10 electives has `group: 'elective', type: 'Elective'`. **Diff: for the current 27-row dataset, `group` and `type` are fully consistent** (no `group: 'core'` row has `type: 'Elective'` or vice versa) — so today, `engine.js`'s `type`-only progress math and the UI's `group`-based styling agree in practice.

**Completeness gap identified:** this consistency is **not enforced anywhere** — nothing validates at data-entry time or at runtime that `group` and `type` agree for a given subject row. Per the README's own "Updating for a New Semester" instructions, the twice-yearly maintenance procedure only mentions updating `lecture`/`exam`/`terms`/`currentTerm` fields — it never mentions `group` or `type`, and a future new subject added to `subjects.js` (LPAB does occasionally restructure its elective list — three IDs in the current list, `16` and above, are non-contiguous with core/compulsory IDs, suggesting past additions) could have these two fields set inconsistently by a maintainer unaware both fields must agree. If that happened, `engine.js`'s graduation-progress bar (`type`-driven) and the visual slot styling / group label (`group`-driven) would silently disagree — a subject could be styled and labeled "Elective" in the UI while counting toward the 17 required "Compulsory" subjects in the progress bar (or vice versa), which is a directly graduation-relevant correctness gap for a tool whose stated purpose is "tracks progress toward graduation." Recorded as candidate bug CB-3 (a completeness/robustness gap rather than a currently-triggered bug, since the present dataset happens to be consistent).
