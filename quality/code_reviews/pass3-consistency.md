## Pair 1: REQ-005 vs REQ-006 (same function, asymmetric term-scoping)

**Finding: CONFIRMED INCONSISTENCY.** Both branches live in `engine.js:64-92`'s single `getClashingSubjects` function. The lecture-clash branch (lines 72-79) is unconditional on `semesterId`. The exam-clash branch (line 81) is gated by `semesterId === currentTerm`. Grepped the entire repository for any comment, README passage, or commit-adjacent rationale (`git log --all --oneline -- engine.js` shows no commit message referencing this distinction) that would justify treating the two clash types differently — found none. This asymmetry within a single function, checking two conceptually parallel things (lecture clash, exam clash) with two different scope policies, is the strongest structural signal in this codebase of an unintentional gap rather than a deliberate design choice. Tracked as BUG-001.

## Pair 2: REQ-007 vs REQ-020 (validation vs. display divergence)

**Finding: CONFIRMED INCONSISTENCY.** `parseExamDate` (REQ-007) is the only validation layer for exam-date strings, and it is architecturally isolated inside `datetime.js` — grep confirms zero external callers besides `examTimesClash`/`sortByExamDate`, both within the same file. `getExamText` (REQ-020, in `ui-board.js`) independently reads `subject.exam` and `historicalExams[...].exam` with no validation step. No shared "get a display-safe, pre-validated exam string" helper exists anywhere in the codebase to reconcile the two. This means a single malformed string can simultaneously satisfy REQ-020's display path (shown as if valid) and violate the *intent* behind REQ-007 (silently excluded from clash protection) — the two requirements, both individually well-implemented, produce a contradictory end-to-end user experience when the underlying data is malformed. Tracked as BUG-003 (grouped with REQ-020[d] since they share one root cause: no shared validation layer).

## Pair 3: REQ-010/REQ-011 (`type`-based) vs REQ-012 (`group`-based)

Not elevated beyond REQ-012's existing architectural-guidance framing.

## Pair 4: REQ-002 (capacity) vs onboarding's `applyPathway`

**Finding: NOT CURRENTLY VIOLATED, but the enforcement gap is real.** As established in Pass 1 (F1-5), `SUGGESTED_PATHWAY`'s per-semester subject+electiveSlot counts never exceed 3 (max), well under the 4-subject cap — so `applyPathway`'s missing failure-handling (REQ-017/BUG-002) cannot currently be triggered via a capacity violation from this specific data. However, this is a **data-value coincidence, not a code guarantee** — if a future edit to `SUGGESTED_PATHWAY` (a hardcoded array with no validation against `engine.js`'s capacity constant) ever pushed a semester's total to 5+, the silent-failure defect in `applyPathway` would immediately become live with zero code changes required elsewhere. This strengthens (rather than replaces) BUG-002's severity assessment — the bug is "dormant but load-bearing," not "theoretical."

## Additional consistency check — export ordering (REQ-021) vs. board rendering ordering

`ui-board.js`'s `renderPlannerBoard` renders semester cards in `allTerms` order (`js/ui/ui-board.js:105-119`), which IS chronological (built via a sequential year-incrementing loop). `ui-toolbar.js`'s `handleExport` (REQ-021) instead sorts alphabetically. This means **the on-screen board order and the exported markdown order can disagree** for any plan spanning a year boundary in certain configurations — a student who exports their plan gets a different semester ordering than what they see on screen. This is a newly-identified consistency finding (not explicitly called out in Phase 1/2, though the underlying alphabetical-sort defect was already tracked as REQ-021/CB-6) — recorded here as additional evidence strengthening BUG-004's severity: it's not just "non-chronological in the abstract," it's "actively inconsistent with the same app's own board view."
